## 1. 背景概述

### 1.1 项目背景与目标

讲座、社团活动、演出和体育赛事等活动通常需要提前报名、按场次和票种限制人数，并在现场核对参与资格。使用聊天接龙或手工表格管理时，容易出现重复报名、超额占位、退票后名额未释放、候补顺序不清以及签到与名单不一致等问题。

本项目面向参与者、活动组织者、检票人员和平台管理员，建立从活动草稿、审核发布到报名、模拟支付、候补递补、验票及统计的完整业务流程。系统的主要目标是：

- 通过活动、场次、票种三级结构维护时间、地点、价格及容量。
- 通过明确的角色权限和数据归属，限制活动管理、交易、检票和平台治理操作。
- 通过状态机、库存占位、唯一性及幂等约束，处理并发竞争、重复请求、超时和取消。
- 为组织者提供名单导出和统计，为管理员提供可查询的关键操作记录。
- 形成能够支撑后续 UML 建模、数据库设计、原型实现与测试的可验收需求。

### 1.2 系统边界

系统负责站内账号、活动与场次管理、公开查询、订单及候补、模拟支付退款、票 id 验票、站内通知、统计导出和审计。支付与退款不发生真实资金流转，但保留成功、失败、超时、重复操作等业务行为；不能因为使用模拟支付而省略一致性处理。

本期明确不实现真实支付、短信、微信、邮件、二维码验票、实名认证、人脸识别、复杂选座、地图、营销和跨平台分发。也不提供代报转赠、角色切换、手机号更换、单场取消、下架恢复、终态恢复、线上申诉、误验撤销及部分退款功能。电子票采用票 id，可下载文本票据；通知采用持久化站内消息和页面提示。

系统可采用单应用和本地持久数据库实现，不要求微服务或分布式资金补偿。原型仍需具备事务、幂等、权限校验和持久化任务恢复能力。范围依据为 REQ-047 及 INT-03-L026、INT-03-L028、INT-03-L030、INT-04-L102。

## 2. 需求分析

### 2.1 用户角色与业务模块

#### 2.1.1 角色与权限

本系统一账号固定一种角色，权限不仅取决于角色，还取决于活动归属或场次授权。所有校验由服务端执行，不能仅依靠隐藏界面按钮。

| 角色 | 主要允许操作 | 关键限制 |
| --- | --- | --- |
| 参与者 | 查询活动、本人报名与候补、模拟支付、合规取消退款、查看本人订单及电子票、举报、查看站内消息 | 不能管理或审核活动、不能执行验票、不能查看完整名单或他人订单 |
| 活动组织者 | 创建草稿、维护场次票种、提交或撤回审核、有限编辑已发布活动、合规整活动取消、查看自己活动名单与统计、导出 CSV | 不能审核、验票、举报或处理平台违规，不能发起支付，不能管理他人活动 |
| 检票人员 | 核对并验授权场次票 id、查看该场名单及签到统计、在结束后且账号仍有效时补做缺席漏标 | 不能购票、举报、修改活动及订单、取消报名、导出名单或跨场验票 |
| 平台管理员 | 审核发布、维护类别和管理账号、分配场次授权、核查举报、基于证据下架、查询审计及支付记录 | 不能代建活动、代报名或代支付，不能无依据下架或直接取消正常用户订单 |

参与者和组织者自行注册；管理员和检票员由管理员鉴权接口创建。每场发布前至少配置一个可用检票账号，一个账号只能授权一个场次，同场允许多个检票账号。管理员新增、重置后的强制改密，会话失效及账号销毁规则见 REQ-028～REQ-032。

以下三项体现主要分析结论：

**需求 ID：REQ-013。需求描述：**候补按场次和票种排队，获得名额后先确认再支付。**分析：**确认期和支付期分别起算，均受场次报名截止约束；候补不占库存，递补待确认才占位，避免12小时确认和15分钟支付互相冲突。

**需求 ID：REQ-014、REQ-045。需求描述：**同用户同场次最多一条有效订单，重复请求只生效一次。**分析：**业务唯一性与请求幂等分开：旧请求始终返回旧订单，取消后主动重报用新请求编号，既防重复又允许合法重报。

**需求 ID：REQ-022、REQ-038。需求描述：**组织者取消和管理员违规下架分别受条件约束。**分析：**提前验票后可能已有签到，取消必须真实检查；平台下架按终止时点结算，已结束终态不回改，不能将所有订单简单清零。

### 2.2 核心流程、数据与状态

#### 2.2.1 主要业务流程

活动管理流程为：组织者保存草稿并维护场次票种，提交审核；管理员通过则同时发布，驳回或组织者撤回则回草稿。提交与发布均校验适用条件，发布时还校验场次授权、每日额度及组织者限制。待审核不可编辑，发布后时间、票价和结构固定，只允许规定范围的简介、海报、地点、容量及停售调整。

普通报名流程为：参与者查询场次并确认本人姓名，提交报名；有可分配名额且无合格在先候补时创建未支付订单并占位，用户确认模拟支付后同事务生成成功支付记录和票，订单变已报名。现场由检票员核对票 id 并确认签到，场次结束后已签到转完成，未签到的已报名订单转缺席。

候补是普通报名的分支：无可分配名额或需要排队时进入候补；系统按稳定顺序分配释放或新增名额，转递补待确认、保留名额并写入站内消息；用户确认后进入未支付，随后完成支付。拒绝或超时则取消并继续递补。

所有开放、确认、支付和验票窗口均以服务器时间判断，含起点、不含终点。普通支付最多15分钟；递补确认最多12小时、确认后支付最多15分钟，实际期限均取与场次报名截止的较早者。截止即时拦截新操作，相关订单最长1分钟内清理。

#### 2.2.2 核心数据对象及关系

| 数据对象 | 主要关系与约束 |
| --- | --- |
| 用户、角色及手机号身份标识 | 每账号一种角色，注销及限制计数按手机号关联；逻辑删除不改变内部编号 |
| 活动、类别、组织者 | 活动属于一个组织者，关联类别编号及名称快照 |
| 场次、票种 | 活动含多个场次，场次含多个票种；场次起止、地点和容量独立，票种容量与价格独立 |
| 报名单 | 一单对应一个用户、一个场次和该场一个票种，记录姓名和金额快照、时限、状态及请求编号 |
| 支付尝试、退款 | 一单可多次失败尝试，但最多一次成功支付和一次成功退款，均保留结果及关联 |
| 票、签到及授权 | 一单最多一票、一签到；票 id 全局唯一，检票账号当前只授权一个场次 |
| 操作日志、站内消息、任务 | 成功日志与必发消息随单项事务持久化，终止任务保存处理进度及判断依据 |
| 举报、违规及限制 | 举报按人和场次去重，同活动同事实处罚一次，限制保存计数依据防重复使用 |

提交时每活动1至20场、每场1至10票种，各票种容量之和不超过场次容量。场次及票种容量为1至9999，价格0至999999元、最多1位小数，以整数角保存。活动级时间、容量和票价区间由下级数据汇总，不重复维护冲突值。

#### 2.2.3 状态及允许转换

活动状态为草稿、待审核、已发布、已取消、已下架、已结束。主要路径为“草稿→待审核→已发布→已结束”；撤回或驳回回草稿，已发布可按条件取消或下架，三个终态不恢复。开售、售罄、停售、截止等是场次或票种的派生展示状态。

订单的稳定状态和主要允许转换如下，完整清单见 requirements.md 附录A：

| 原状态 | 目标状态 | 触发条件 |
| --- | --- | --- |
| 无订单 | 未支付／候补中 | 通过资格检查，依据名额和队列情况分别处理 |
| 候补中 | 递补待确认 | 系统分配名额、占位并写入通知 |
| 递补待确认 | 未支付 | 确认期内确认，沿用原占位并起算支付期 |
| 未支付 | 已报名 | 支付与出票同事务成功，内部经过已支付步骤 |
| 候补中／递补待确认／未支付 | 已取消 | 合法主动取消、相应超时、失败达到上限、截止或活动终止 |
| 已报名 | 已签到 | 在有效窗口内对有效票授权验票 |
| 已报名 | 已退款 | 合规主动退款或平台终止退款成功 |
| 已报名 | 缺席 | 场次正常结束仍未签到 |
| 已签到 | 已完成 | 场次正常结束或平台提前终止结算 |

“已支付”是事务内中间步骤，不独立提交为用户长期停留状态；“已递补”只作操作标签，以“递补待确认”表示等待阶段。支付失败保持未支付；退款失败回滚并保留原票和占位。

禁止已签到转取消、退款或缺席；禁止已完成、已取消、已退款、缺席恢复为其他订单状态。已报名取消须通过退款，不能直接改已取消。已取消后如需重报须新建订单。票状态区分有效、已验票、已失效，重复验票只查首次结果，不恢复票。

#### 2.2.4 唯一性与库存一致性

同用户同场次最多一条有效订单，不因票种不同而放宽。候补中、递补待确认、未支付、已报名、已签到属于有效状态，用于唯一性及时间冲突检查；候补有效不代表占名额。

库存采用以下统一定义：

> 票种已占名额＝未支付占位数＋递补待确认占位数＋成功出票且未退款订单数。  
> 票种剩余名额＝票种容量－已占名额，且必须大于或等于0。

未退款出票数包含已完成及缺席历史，避免已售票因结束状态再次变可售。场次余票为各票种余票加总，不把未分配给票种的容量当可售票。确认和支付沿用原占位，不能再次扣库存；取消及退款只释放一次。发布后缩容不得低于占用数量，扩容优先递补。

报名、退款、递补、扩缩容及冲突检查必须在服务端原子执行。单项业务变更、成功日志和必发消息一并提交；全活动终止可以分批，但每单幂等，处理进度持久化。

#### 2.2.5 异常、取消及下架处理

| 场景 | 最终处理 |
| --- | --- |
| 20人抢最后一名额 | 恰好1人占位，其余合格19人候补；支付不再次扣名额 |
| 重复报名／取消后旧请求重放 | 返回原请求订单；新报名意图须新编号，另查有效订单唯一性 |
| 支付失败或超时 | 不同尝试失败允许重试，连续3次失败或先超时取消；重放同一失败尝试不加次数 |
| 截止后旧页面提交 | 立即拒绝新操作；到期清理不成为放行条件 |
| 重复／越权验票 | 有效账号授权范围内返回首次签到结果；失效账号或无授权先拒绝 |
| 组织者主动取消 | 仅限首场开始前且全活动无签到；未支付类取消，成功出票订单退款、票失效 |
| 管理员违规下架 | 即时阻止新交易和验票；尚未结束场次未签到成功订单全退，已签到保留并完成，已结束终态不回改 |
| 响应丢失／任务重启 | 按请求编号查询最终结果；从持久化待办继续执行，不重复处理 |

组织者不能通过“先下架再修改”恢复发布活动。时间或票价确需调整时，只能在允许取消时取消后新建，不迁移旧票或候补。自然结束后缺席才能计入相应购票约束，平台中止导致未入场者退款，不新增缺席处罚。

下架退款按终止状态提交时的时间及签到事实判断，不能因任务晚执行而改变资格。管理员只能重试有依据的失败退款，不能任意取消正常订单。活动终止后的订单统一处理和报表须在5分钟内完成。

#### 2.2.6 统计、导出与数据保留

正式统计在场次结束结算后生成，整活动终结后汇总。报名人数为曾成功出票订单数，另列退款数；签到率及缺席率分母均为未退款成功出票数，包含免费票。签到率为签到数除以该分母，缺席率为缺席数除以该分母；零分母时两率均为0。容量利用率为签到数除以结束时场次容量。活动汇总加总分子分母后计算，不平均百分比；跨场按人次统计。

当前候补数与累计候补申请数分别展示，避免截止清理使历史需求归零。进行中仅提供实时订单状态数、余票、候补和签到数，不将其冒充最终报表。

组织者和管理员按权限导出 CSV，包含姓名、场次、票种、报名状态、签到状态和票码。文件用带BOM的UTF-8，正确处理分隔符和公式起始文本；生成和每次下载均鉴权，空名单输出表头。

名单、统计及导出统一至活动实际终结后7天，所有角色到期拒绝读取及系统重建；晚生成导出不续期。个人订单、票及支付记录继续按权限保留，账号注销不级联删除业务。日志生成后180天物理清理，消息180天逻辑删除，手机号注销计数及黑名单长期保留。两次注销至少间隔365天，第3次后该手机号禁止再注册。

## 3. 非功能性需求

## 4. 结论

当前需求已覆盖课程要求的四类角色、活动与场次票种管理、查询报名、候补递补、验票缺席、统计导出、关键日志，以及重复操作、并发、超时和状态冲突。最终53条需求中，47条功能需求、5条非功能需求和1条约束均有验收方法；状态字段为32条“已确认”、21条“已变更”，后者表示旧规则被本版替代，并非仍执行旧版本。

文档复核检查了唯一连续编号、10个必填字段、来源和关联有效性，以及第四轮52组答复的覆盖，并补充13条允许状态转换、18个交叉验收场景。该结果足以支持后续用例、状态机和数据库设计；软件功能、性能和故障恢复仍需实现后验证。

## 附：需求整理与会谈内容

### A. 业务问题与关键会谈要点

以下选取能解释需求决策的少量会谈内容；完整访谈、提示词、初稿和审查保存在 chat.txt，不以本附录替代原始记录。

**活动容量：**INT-01-L011 询问活动、场次和票种的关系。INT-01-L012 回答每场有独立容量，每场可分多个票种，票种容量之和不超过场次容量。由此形成三级结构与 REQ-005，而不是只在活动级维护一个库存。

**模拟支付：**INT-01-L026 明确没有真实资金流转，但未支付、已支付、已退款及失败、超时、重复支付均要处理。由此保留支付尝试、退款记录及幂等约束，避免把“模拟”理解为无需状态一致性。

**验票方式：**INT-03-L029 追问二维码与票id的冲突；INT-03-L030 回答“使用票id，不使用二维码”。最终 REQ-017、REQ-040 只采用票id，删除旧模板中的扫码描述。

**候补时限：**INT-03-L006 将确认期限统一为通知后12小时；第四轮 INT-04-L002、L006 进一步明确确认和支付分阶段且不超过报名截止。最终规则体现为 REQ-011、REQ-013，不再沿用24小时假设。

**账号与审计：**INT-03-L018 明确检票账号销毁后日志独立保留180天；INT-04-L054、L080 进一步区分账号逻辑删除、底层业务记录、短期报表和日志。最终由 REQ-021、REQ-032、REQ-052 分别约束。

### B. 后续设计与测试的关键场景

1. 报名18:00截止，17:50递补，实际确认和支付都必须在18:00前完成。
2. 活动10:00开始，9:40已有签到，9:45组织者取消应被拒绝。
3. 取消后旧请求重放返回旧单，新的报名请求在资格允许时创建新单。
4. 支付已提交但响应丢失，刷新或原请求重试只返回结果，不重复出票。
5. 下架处理到一半重启，按终止时保存的事实续办，不因执行时间变化改变退款资格。

7. 同账号同场不同票种并发报名，只能保留一条有效订单。
8. 同一票并发验票只成功一次；账号已销毁时先拒绝登录，不为查询已签到结果恢复账号。
