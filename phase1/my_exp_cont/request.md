# 需求分析报告

项目名称：活动票务与报名系统

版本：version1    日期：2026/10/9    学号：241220089   姓名：蔡杨杨


## 1. 项目背景、目标与系统边界

### 1.1 项目背景

活动票务与报名系统是一个面向参与者、活动组织者、检票人员和平台管理员，支持活动发布、报名购票、模拟支付、候补递补、检票签到及名单统计的在线票务管理平台。讲座、演出、社团活动、体育赛事等往往需要提前统计人数并按票种控制容量，人工报名容易出现重复报名、超额、名单混乱和签到无法核对等问题，因此需要一个具备角色权限、支付状态流转、容量约束、异常处理和操作记录的系统。

### 1.2 项目目标

- 支持活动、场次、票种的创建、审核、发布、修改和取消；
- 支持按类别、时间、地点、票种、价格区间和状态的多条件查询；
- 支持报名购票、模拟支付、取消报名与退款、候补排队和自动递补；
- 支持验票签到、缺席标记以及名单导出；
- 支持报名、支付、候补、签到等统计汇总和关键操作记录；
- 满足明确的性能、并发、安全、可靠性和易用性要求。

### 1.3 系统边界与明确不实现的内容

系统负责活动从创建到结束的全过程管理与状态一致性；身份核验、通知渠道、座位编排等真实外部能力不由本系统实现。

关于支付：系统不接入真实支付渠道、不发生真实资金流转，但提供“确认支付”按钮模拟用户支付，并完整维护未支付、已支付、已退款等支付状态及支付超时、失败、重复支付等异常处理，以保证后续设计、实现和测试可覆盖支付流程。

以下内容明确不实现（标注为“假设”，待甲方确认）：

- 不接入真实支付渠道，不产生真实资金结算，“确认支付”仅模拟支付动作；
- 不接入真实短信、微信或邮件通知，递补通知以站内消息或模拟方式表述；
- 不实现实名认证、人脸识别等真实身份核验；
- 不实现复杂座位图选座，仅按票种和容量管理；
- 不实现第三方地图、营销或跨平台分发。

## 2. 需求分析

### 2.1 用户角色与业务模块

本系统包含参与者、活动组织者、检票人员和平台管理员四类角色，权限边界如下：

- 参与者：可浏览已发布活动、提交报名单、通过“确认支付”按钮模拟支付、取消报名或申请退款、进入候补、查看自己的报名记录和电子票、现场签到。不能创建或修改活动、不能审核活动、不能验票。
- 活动组织者：可创建活动草稿、维护场次和票种、提交审核、修改已发布活动、取消活动、查看报名名单、导出名单。不能审核自己提交的活动、不能代替检票人员验票、不能处理平台级违规。
- 检票人员：可对指定场次进行验票、签到、标记缺席、查看签到统计。不能修改活动信息、不能修改报名记录、不能取消报名。
- 平台管理员：可审核活动、驳回违规活动、下架已发布活动、处理举报、查看全部操作记录。不能代替组织者创建活动、不能代替参与者报名。

按模块概括需求（功能需求编号 REQ-001～REQ-015，非功能需求编号 REQ-016～REQ-020；完整字段与验收方法见 requirements.md）：

- 活动管理模块（REQ-001～REQ-004）：组织者创建活动草稿、维护场次与票种、提交审核；管理员审核通过后发布，驳回则退回草稿；组织者可取消已发布活动。
- 查询模块（REQ-005）：参与者按活动类别、时间、地点、票种、价格区间和活动状态多条件查询已发布活动。
- 报名、支付与候补模块（REQ-006～REQ-010）：参与者提交报名单，通过“确认支付”按钮模拟支付，报名单经历未支付、已支付、已报名等状态；名额已满时进入候补；有人取消后按候补队列顺序自动递补；同一用户同一场次同一票种只允许一条有效报名单。
- 检票签到模块（REQ-011～REQ-013）：检票人员扫码或输入票码验票；重复签到返回已签到；活动结束后未签到自动标记缺席；组织者可导出签到名单和缺席名单。
- 统计与审计模块（REQ-014～REQ-015）：组织者和管理员可查看报名人数、候补人数、签到率、缺席率、容量利用率；关键操作保留可查询的操作记录。

### 2.2 核心流程、数据与状态

主要业务流程：

组织者创建活动草稿 → 维护场次和票种 → 提交审核 → 管理员审核 → 发布活动 → 参与者提交报名单（未支付）→ 点击“确认支付”模拟支付 → 支付成功出票（已报名）→ 名额已满进入候补 → 有人取消自动递补 → 活动截止 → 现场检票签到 → 活动结束 → 统计名单和签到率。

核心数据对象及关系：

- 用户与活动：一个组织者可创建多个活动，一个活动只属于一个组织者。
- 活动与场次：一个活动可包含多个场次，每个场次独立容量。
- 场次与票种：一个场次可包含多个票种，每个票种独立容量和价格，票种容量之和不超过场次容量。
- 报名单与用户、场次、票种：一条报名单唯一关联一个用户、一个场次和一个票种。
- 支付记录与报名单：一条报名单对应一次有效支付，记录支付状态、支付时间和模拟支付结果。
- 候补记录与报名单：候补按报名时间排序，取消后自动递补。
- 签到记录与报名单：一条报名单最多一条有效签到记录，重复签到不新增记录。
- 操作记录：记录报名、支付、退款、取消、递补、签到、审核、取消活动等关键操作。

唯一性和一致性规则：

- 同一用户在同一场次同一票种下只能有一条有效报名单。
- 一条报名单同时只能存在一条有效支付记录，重复支付返回原支付结果，不重复扣减名额或生成票码。
- 报名人数不能超过票种容量，票种已报名人数之和不能超过场次容量。
- 候补队列顺序必须稳定，递补按顺序进行。
- 票码全局唯一，重复签到不产生第二条签到记录。
- 活动取消后，所有未支付、已支付和候补记录必须统一处理并保留操作记录。

核心业务对象状态（以报名单为例）：

> 未支付 → 已支付 → 已报名 → 已签到 → 已完成

辅助状态：候补中、已取消、已退款、缺席、已递补。

允许的转换：

- 未支付 → 已支付（点击“确认支付”，模拟支付成功）
- 未支付 → 已取消（支付超时或用户主动放弃，释放名额）
- 已支付 → 已报名（支付成功并完成出票，生成票码）
- 已报名 → 已退款（截止前取消已支付订单，模拟退款完成）
- 未支付 → 候补中（名额已满）
- 候补中 → 已取消（参与者取消候补）
- 候补中 → 未支付（有人取消，按候补顺序递补后进入待支付）
- 已报名 → 已签到（现场验票）
- 已签到 → 已完成
- 已报名 → 缺席（截止后未签到）

禁止的转换：

- 已签到 → 已取消
- 已完成 → 已取消／已退款
- 已支付 → 未支付（支付状态不可回退，只能进行退款）
- 已取消 → 已报名（除非重新报名并重新支付，需按访谈确认）
- 已退款 → 已报名（已退款订单不可直接恢复）
- 已截止 → 未支付／已报名

失败、撤销或冲突处理：

- 并发抢最后一个名额：仅允许一人成功，其余进入候补或返回失败。
- 重复提交报名：返回原报名单，不新增记录。
- 重复支付或旧页面重复点击“确认支付”：返回原支付结果，不重复扣减名额或生成票码。
- 支付超时：未支付报名单在约定时限内未完成支付，自动转已取消并释放名额，触发候补递补。
- 支付失败：保持未支付并允许重新支付；连续失败或超时后转已取消。
- 支付后退款：截止前取消已支付报名单，模拟退款完成后转已退款。
- 截止后报名或支付：系统拒绝并返回“报名已截止”。
- 候补递补通知超时：视为放弃，继续递补下一位。
- 重复签到：返回“已签到”，不新增签到记录。
- 活动取消：统一处理未支付、已支付、已报名和候补记录，已支付的按规则模拟退款并保留操作记录。

## 3. 非功能性需求

性能示例（REQ-016）：约定测试环境、1 万条活动、50 并发用户下，100 次活动查询至少 95 次在 1 秒内成功返回；失败和超时计入未达标次数。

并发示例（REQ-017）：约定测试环境，最后一个名额被 20 个并发请求同时抢，只能 1 人报名成功，其余进入候补或返回失败，报名人数不得超过票种容量。

安全示例（REQ-018）：票码在同一场次同一票种下全局唯一；检票人员只能对授权场次验票；参与者只能查看自己的报名单、支付记录和电子票。

可靠性示例（REQ-019）：关键操作记录至少保留 180 天，可按操作人、操作类型、时间范围查询；支付操作具备幂等性，重复提交不产生重复支付记录；活动取消后 5 分钟内完成未支付、已支付、已报名和候补记录的状态统一。

易用性示例（REQ-020）：参与者从活动详情页到完成报名与模拟支付，在正常网络下不超过 3 步操作；检票人员单次验票操作不超过 2 步。

## 4. 需求中的歧义、冲突、假设及处理结果

- 歧义：报名是否等同于购票、支付如何处理。处理：报名与购票合并为一条报名单流程，通过“确认支付”按钮模拟支付并维护未支付、已支付、已退款等状态，不接入真实支付渠道、不发生真实资金流转；支付超时、失败和重复支付的判定规则待甲方确认。
- 歧义：已取消报名能否重新报名。处理：假设允许重新报名并按当前时间重新排队，最终状态转换待甲方确认。
- 歧义：候补递补通知的等待时长。处理：假设通知后 24 小时内未确认视为放弃，待甲方确认。
- 冲突：票种容量与场次容量的关系。处理：约定各票种容量之和不超过场次容量，报名人数不超过对应票种容量。
- 冲突：重复签到与签到统计的一致性。处理：重复签到不新增记录，统计以有效签到记录为准。
- 冲突：未支付报名单对名额的占用与超时释放。处理：未支付报名单在支付时限内临时占用名额，超时未支付自动取消并触发候补递补。
- 假设：关键操作记录保留 180 天；若甲方另有合规要求则调整。
