# 需求分析报告

项目名称：活动票务与报名系统

版本：vesion1    日期：2026/10/9    学号：241220089   姓名：蔡杨杨


## 1. 背景概述

活动票务与报名系统是一个面向参与者、活动组织者、检票人员和平台管理员，支持活动发布、报名购票、候补递补、检票签到及名单统计的在线票务管理平台。

## 2. 需求分析

### 2.1 用户角色与业务模块

本系统包含参与者、活动组织者、检票人员和平台管理员四类角色，权限边界如下：

- 参与者：可浏览已发布活动、报名或购票、取消报名、进入候补、查看自己的报名记录和电子票、现场签到。不能创建或修改活动、不能审核活动、不能验票。
- 活动组织者：可创建活动草稿、维护场次和票种、提交审核、修改已发布活动、取消活动、查看报名名单、导出名单。不能审核自己提交的活动、不能代替检票人员验票、不能处理平台级违规。
- 检票人员：可对指定场次进行验票、签到、标记缺席、查看签到统计。不能修改活动信息、不能修改报名记录、不能取消报名。
- 平台管理员：可审核活动、驳回违规活动、下架已发布活动、处理举报、查看全部操作记录。不能代替组织者创建活动、不能代替参与者报名。

按模块概括需求：

注意此处的需求序号后续需要更改

- 活动管理模块（REQ-001～REQ-004）：组织者创建活动草稿、维护场次与票种、提交审核；管理员审核通过后发布，驳回则退回草稿；组织者可取消已发布活动。
- 查询模块（REQ-005）：参与者按活动类别、时间、地点、票种、价格区间和活动状态多条件查询已发布活动。
- 报名与候补模块（REQ-006～REQ-010）：参与者报名或购票；名额已满时进入候补；有人取消后按候补队列顺序自动递补；同一用户同一场次同一票种只允许一条有效报名单。
- 检票签到模块（REQ-011～REQ-013）：检票人员扫码或输入票码验票；重复签到返回已签到；活动结束后未签到自动标记缺席；组织者可导出签到名单和缺席名单。
- 统计与审计模块（REQ-014～REQ-015）：组织者和管理员可查看报名人数、候补人数、签到率、缺席率、容量利用率；关键操作保留可查询的操作记录。

### 2.2 核心流程、数据与状态

主要业务流程：

组织者创建活动草稿 → 维护场次和票种 → 提交审核 → 管理员审核 → 发布活动 → 参与者报名或购票 → 名额已满进入候补 → 有人取消自动递补 → 活动截止 → 现场检票签到 → 活动结束 → 统计名单和签到率。

核心数据对象及关系：

- 用户与活动：一个组织者可创建多个活动，一个活动只属于一个组织者。
- 活动与场次：一个活动可包含多个场次，每个场次独立容量。
- 场次与票种：一个场次可包含多个票种，每个票种独立容量和价格，票种容量之和不超过场次容量。
- 报名单与用户、场次、票种：一条报名单唯一关联一个用户、一个场次和一个票种。
- 候补记录与报名单：候补按报名时间排序，取消后自动递补。
- 签到记录与报名单：一条报名单最多一条有效签到记录，重复签到不新增记录。
- 操作记录：记录报名、取消、递补、签到、审核、取消活动等关键操作。

唯一性和一致性规则：

- 同一用户在同一场次同一票种下只能有一条有效报名单。
- 报名人数不能超过票种容量，票种已报名人数之和不能超过场次容量。
- 候补队列顺序必须稳定，递补按顺序进行。
- 票码全局唯一，重复签到不产生第二条签到记录。
- 活动取消后，所有有效报名单和候补记录必须统一处理并保留操作记录。

核心业务对象状态（以报名单为例）：

> 待确认 → 已报名 → 已签到 → 已完成

辅助状态：候补中、已取消、缺席、已递补。

允许的转换：

- 待确认 → 已报名（确认成功）
- 待确认 → 候补中（名额已满）
- 候补中 → 已报名（有人取消，自动递补）
- 已报名 → 已取消（截止前）
- 已报名 → 已签到（现场验票）
- 已签到 → 已完成
- 已报名 → 缺席（截止后未签到）

禁止的转换：

- 已签到 → 已取消
- 已完成 → 已取消
- 已取消 → 已报名（除非重新报名，需按访谈确认）
- 已截止 → 已报名

失败、撤销或冲突处理：

- 并发抢最后一个名额：仅允许一人成功，其余进入候补或返回失败。
- 重复提交报名：返回原报名单，不新增记录。
- 截止后报名：系统拒绝并返回“报名已截止”。
- 候补递补通知超时：视为放弃，继续递补下一位。
- 重复签到：返回“已签到”，不新增签到记录。
- 活动取消：统一处理已报名和候补记录，并保留操作记录。

## 3. 非功能性需求

性能示例（REQ-016）：约定测试环境、1 万条活动、50 并发用户下，100 次活动查询至少 95 次在 1 秒内成功返回；失败和超时计入未达标次数。

并发示例（REQ-017）：约定测试环境，最后一个名额被 20 个并发请求同时抢，只能 1 人报名成功，其余进入候补或返回失败，报名人数不得超过票种容量。

安全示例（REQ-018）：票码在同一场次同一票种下全局唯一；检票人员只能对授权场次验票；参与者只能查看自己的报名单和电子票。

可靠性示例（REQ-019）：关键操作记录至少保留 180 天，可按操作人、操作类型、时间范围查询；活动取消后 5 分钟内完成报名单和候补记录的状态统一。

易用性示例（REQ-020）：参与者从活动详情页到完成报名，在正常网络下不超过 3 步操作；检票人员单次验票操作不超过 2 步。
