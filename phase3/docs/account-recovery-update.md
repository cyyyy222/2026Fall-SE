# 注册、密码找回、人工申诉与个人信息换绑

日期：2026-11-03。本文落实用户最新确认，优先于此前“邮箱必填、普通用户不能改手机号、人工找回只填两项”的旧说明。前一版手机号跨角色和检票账号规则仍见[账号与登录调整](account-auth-update.md)。

## 注册提示与邮箱

此前前端只显示后端统一的“请求字段不合法”，无法看出是密码、邮箱还是验证码字段不符合要求。本次改为按字段显示明确原因；例如密码须为8～72位ASCII字母数字组合、验证码必须六位、需要先获取验证码。没有保存用户此前失败请求的具体输入，因此不将某一种猜测写成该次失败的确定原因。

邮箱现为选填，省略、null和空白统一保存为SQL NULL；多个账号均可不填。填写时trim后按通用邮箱格式校验，不使用后缀白名单，支持qq.com、foxmail.com、163.com、edu.cn等合法邮箱域名；不验证邮箱实际收件能力。已填写的邮箱仍在有效账号中唯一，用户名仍全局唯一。

注册仍需手机验证码，并按角色限制手机号：一个号码可分别绑定参与者、组织者各一个有效账号，同角色不得重复。重复注册经验证码确认后可选择登录原账号，不覆盖原账号。

## 优先验证码找回

登录页 → 忘记密码 → 手机号验证码找回：选择参与者/组织者，填写已绑定手机号，获取RESET_PASSWORD用途验证码，设置并确认新密码。无需原密码。验证成功后撤销全部旧会话、清Cookie，用户重新登录。管理员和检票员无手机号，继续由其他管理员按原权限处理。

新增`POST /api/auth/password-reset`（AUTH-08）；不自动创建账号，不允许把登录/注册/换绑验证码用于密码重置，反过来也不允许。

## 原号不可用时提交详细申诉

“原号不可用，人工申诉”表单填写：

- 原账号用户名、角色、账户原手机号。原号指丢失访问时账号实际绑定的号码，不一定是最初注册号码。
- 当前可用手机号；先使用RECOVERY_CONTACT验证码证明持有，用于接收处理通知。
- 20～2000字申诉陈述，说明原号码为何不可用、注册情况及其他核验信息。
- 20～2000字以往行为信息，例如报名/自建活动、时间、票种、订单状态等。不要提供密码。

提交后只生成PENDING申请，不直接改密。服务端按用户名、角色和原手机号冻结匹配的原账号UUID，后续同名重注册不会改绑目标；未匹配也统一受理，不向匿名请求泄露账号是否存在。当前号码必须通过验证码，陈述只是待核实线索，不能自动成为通过审核的依据。

管理员在“账号找回申请”查看原号、当前号、陈述及行为信息，另有系统匹配的注册时间和最多5笔本人订单/自建活动摘要辅助核对；不提供活动参与者名单。核对后填写至少10字审核依据，选择驳回或“审核通过，换绑并重置密码”，并设置临时密码。

通过及改密在同一个MySQL事务内完成，重新检查原账号未被注销或换绑、当前号未被同角色其他账号占用；同时更新登录号码、密码哈希、强制改密标记及旧会话状态。事务失败不输出成功短信。相同幂等键重放不重复发送。

### 模拟短信通知

按用户授权，只在local环境输出：

```text
[LOCAL_RECOVERY_SMS] phone=当前手机号 account=用户名 initialPassword=临时密码 recoveryId=申请编号 mustChangePassword=true
```

该日志在事务提交后输出；不把临时密码保存为可回查数据库字段、普通审计内容或API响应。原验证码日志继续使用`LOCAL_PHONE_CODE`。可以在启动后端的终端查看，也可以在VS Code中运行：

```powershell
cd D:\2026Fall-SE\phase3\code\backend
Get-Content .\backend-local.log -Tail 30 -Wait
```

通知仅为本地模拟，不连接真实短信供应商。用户用临时密码登录后必须修改密码。旧版缺少当前号验证和详细陈述的申请不能直接重置，应由管理员核对并退回后重新提交完整资料。

## 在个人信息中换绑

入口：右上角账号菜单 → 账号与安全 → 本人资料 → 绑定手机号旁的“换绑手机号”。

**只需要新手机号验证码，不要求原号验证码或原密码。** 用户已通过当前登录会话鉴权。获取CHANGE_PHONE验证码和最终保存时均检查新号占用：同角色被占用则拒绝，另一角色绑定不影响；新号与当前号相同也会提示。客户端不能传入其他用户ID或选择操作者。

新增`PATCH /api/me/phone`（ME-27），保存带原幂等键，成功后撤销旧登录并要求重新登录。用户名、角色、原账号密码、本人订单、票和历史业务事实均保留。

### 登录联系方式与历史业务身份

users新增可空的`login_phone_identity_id`。为空时，登录联系方式沿用原`phone_identity_id`；换绑后由新字段指向当前登录号码。原`phone_identity_id`保留为历史业务身份，避免换绑清空原订单事实、注销计数或已有处罚；现行限制查询同时考虑原业务身份和新登录号码。展示、手机号登录、原号匹配及唯一占用按当前联系方式计算。

生成列`active_phone_identity_id`改为有效账号的`COALESCE(login_phone_identity_id,phone_identity_id)`，原`uk_user_phone_role`复合唯一索引继续保护同角色当前号码的并发唯一性。这个设计不修改已保存订单的身份快照，也不把换绑实现为新建账号或合并账号。
