## 2. 分层和数据访问方式

Controller → XxxServiceImpl（强类型用例门面）→ service/core用例实现 → RecordStore DAO接口 → JdbcRecordStore → MySQL。复杂用例仍属于Service层，不增加HTTP调用或重复Repository层。SQL仅在DAO里；Controller不访问数据库。Redis通过独立RedisTransientDao访问，不作为业务事实来源。

JdbcRecordStore以固定SchemaRegistry注册33个Entity/表名，通过封闭Filter/Sort构造参数化SQL。字段名必须是已注册Java record属性，不能由HTTP传入任意表名/SQL。UUID、金额、时间、布尔和nullable字段映射已编写；写入和FOR UPDATE要求Service写事务。全站自然日额度有独立的原子建行SQL，避免首条额度并发创建竞争。

前阶段的XxxDao端口保留供后续需要时拆分专用查询；当前实际业务注入的是RecordStore及其Jdbc实现，**不是已经存在33个独立JdbcXxxDao实现**。Entity不作为HTTP返回值，Requests/Queries/Views字段继续按api.md。

写事务使用READ_COMMITTED；多SQL报表读取使用只读REPEATABLE_READ快照。退款创建方法不添加外层事务：T1提交后再进入T2。终止单项的订单变更/退款成功结果及进度同事务提交；失败退款尝试先保存，再由执行器记重试，原deadline不重算。权限和保留期在当前用例读取/写边界检查，不从Redis恢复过期名单。

## 5. 本轮交叉检查中修正的细节

- 365天约束是两次成功注销之间的间隔，不是禁止注销后365天内重新注册；重注册继承手机号历史和限制。
- 简介允许空；公开详情保留同活动下已结束场次并显示结束状态，公开列表才过滤结束场次。
- 草稿替换/重命名先在事务内释放原名称，避免交换名称或用新子ID替换同名对象时触发旧行唯一约束。
- 递补确认后另建15分钟支付截止任务，不沿用原12小时确认任务等待清理。
- 不同退款依据不能借用同单另一依据的成功结果；平台退款不误记主动退款。
- 会话与消息的固定期限使用同一个创建时间锚点，避免多次读取毫秒时钟使DDL精确期限约束失配。
- 含口令写请求的幂等指纹使用规范摘要再经BCrypt保护，重放使用matches核对；不把它存成可快速猜测口令的普通SHA256摘要。现有CHAR(64)可容纳60字符BCrypt指纹。
- 过滤器认证的内部principal关联会话记录ID，写事务取得账号锁后再次核对撤销状态，避免仅凭过滤器旧快照继续写入。
- 管理员审计返回的订单投影不带参与者支付/下载等allowedActions。
- 任务重试不延期，成功但超时的任务仍显示overdue。
- 前端消息只做两处契约对齐：采用服务端首次readAt；按ACCOUNT/EVENT/ORDER及角色导航，参与者不会被送进管理员活动页。页面风格和默认mock未改。

以上规则仍需接库验证其持久化和竞争行为。后续验收以真实结果更新，不把“代码已写”换成“实验已通过”。
