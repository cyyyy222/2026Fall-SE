## 2. 产品范围与边界

目标是实现可本地运行、可持久化、四种角色能走通业务的课程票务产品原型。

| 身份 | 核心能力 | 数据边界 |
| --- | --- | --- |
| 访客 | 查询场次、活动详情、注册、登录、申请人工找回 | 仅公开活动数据 |
| PARTICIPANT 参与者 | 本人报名/候补、支付退款、票、历史、举报、消息及账号安全 | 本人账号和本人业务 |
| ORGANIZER 组织者 | 自己活动的草稿、审核申请、发布后管理、名单、导出、统计 | 自己活动；可浏览公开活动 |
| CHECKER 检票员 | 当前授权场次核对/确认验票、名单、签到统计、结束补漏 | 当前唯一授权场次 |
| ADMIN 管理员 | 审核、账号授权、类别、治理、支付审计、合法退款重试、任务进度 | 明确管理权限内；仍受保留期限制 |

一账号一固定角色，四种角色互不继承；管理员没有代建活动、代报名、代支付、任意取消正常订单的能力。

不接真实支付、短信/微信/邮件；站内消息必须持久化。不实现二维码、实名/人脸识别、复杂选座、地图、营销、代报转赠、角色切换、单场取消、终态恢复、处罚线上申诉、部分退款、撤销验票及过期报表恢复。

## 3. 技术方案与运行拓扑

| 层 | 方案 | 约束 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Vite；Vue Router、Pinia | 浏览器应用；统一 API 层；不把模拟数据写入页面组件 |
| 后端 | Java + Spring Boot；Spring Web、Validation、Security | 模块化单体，REST/JSON；不拆微服务 |
| 业务持久化 | MySQL 8.4 / InnoDB + Spring JDBC + Flyway | DAO接口及Jdbc实现隔离SQL；不依赖ORM自动建表 |
| 短期辅助数据 | Redis / StringRedisTemplate | 限流策略及Lua适配器已编写，默认未连接；可选缓存关闭，不维护第二份业务事实 |
| 事务 | MySQL事务、行锁、条件唯一约束 | Service事务边界；业务、成功日志、必发消息与幂等结果同事务 |
| 文件 | 服务端受控本地目录 | 海报与短期 CSV；私有文件不直接挂静态目录 |
| 构建 | Maven Wrapper、npm 锁文件 | 初始化时锁定相容的 JDK/Node/依赖版本并记录；本文不假定环境已具备 |

开发拓扑：浏览器 → Vite（计划 5173）→ `/api` 代理 → Java（计划 8080）→ MySQL（业务）/Redis（短期辅助）/受控文件。`/api` 原路径保留，前端不硬编码后端域名。开发服务器只监听本机。

交付拓扑：浏览器 → Java（8080，同时提供前端静态文件和 API）→ MySQL（业务）/Redis（短期辅助）/受控文件。使用 Vue Router 的 hash 路由，示例 `http://localhost:8080/#/events`，避免刷新深层页面时与 API/文件路由冲突。以下路由表均省略 `#`。

用户于2026-11-02明确改用MySQL+Redis，原SQLite/BEGIN IMMEDIATE方案被替代。MySQL事务内用行锁、唯一约束和统一锁顺序保护库存、有效订单、退款与发布额度；Redis只承担技术限流及允许短期丢失的辅助数据，不作为权威库存、会话撤销、幂等结果或任务进度。普通查询不加写锁，锁等待/死锁按完整事务回滚及有限重试处理，详见[后端事务设计](backend-plan.md)。

## 9. 核心响应路径与状态

### 9.1 活动

`DRAFT → PENDING_REVIEW → PUBLISHED → CANCELLED / TAKEN_DOWN / ENDED`；待审可撤回/驳回/条件失效退回 DRAFT。终态不恢复、不互转。“开售、停售、售罄、截止”为场次/票种派生字段，不另造活动状态。

草稿使用嵌套聚合整体保存（允许不完整），场次和票种使用稳定 UUID。提交后冻结待审内容。发布时重查完整性、类别、排期、放票时间、组织者限制、每日100额度和每场至少一个可用检票账号。发布失败而必须退草稿时，**提交退回结果、原因、日志和消息**，使用 API 定义的业务结果返回，不能抛异常导致退回也回滚。

发布后只允许简介/海报及未结束场次地点、容量、票种停售修改；不增加/删除场次票种，不改名称/类别/时间/价格；容量编辑必须同时验证票种和场次总容量与占用。

### 9.2 报名、候补、支付

页面 → ME-06 → 会话/角色 → 幂等查重 → 最新活动、开放窗口、停售、手机号限制 → 同场有效唯一/跨场冲突 → 库存及在先合格候补 → 创建 UNPAID 占位或 WAITLISTED 不占位 → 事务提交 → 前端按真实状态导航。

订单稳定状态：`WAITLISTED`（候补中）、`OFFERED`（递补待确认）、`UNPAID`、`REGISTERED`、`CHECKED_IN`、`COMPLETED`、`CANCELLED`、`REFUNDED`、`ABSENT`。允许路径完整定义见 API 状态表；不提交 PAID 或 PROMOTED 状态。

候补按受理时刻和订单编号排序，仅返回本人位次。新增/释放名额优先分配合格在先候补；锁定用户保位但跳过，停售暂停新分配；已占位用户可继续确认/支付。通知和 OFFERED 占位同事务；确认期限=min(通知写入+12小时,报名截止)，确认后支付期限=min(确认时刻+15分钟,报名截止)，确认/支付不重复扣库存。

支付每个新尝试有新 attemptId；响应未知必须重放原 attemptId。普通模式默认成功，模拟失败只能测试注入；第三个不同失败尝试取消并释放。成功支付、票、订单、日志、消息一个事务提交。

### 9.3 取消与退款

WAITLISTED/OFFERED/UNPAID 截止前可取消；REGISTERED 走显式退款确认；CHECKED_IN/COMPLETED/ABSENT 不可退。退款先在受理事务固化合法申请依据，再在单项执行事务提交退款、票失效、订单状态、释放、日志、消息；执行失败回滚本次业务变更，但保留先前合法依据与失败尝试。这是 phase2 退款依据模型的具体落地。普通接口同步尝试执行，不引入订单 REFUNDING 状态。

存在未撤销待处理申请时禁止注销；参与者可撤销未成功的本人申请。重试不能绕过当前已签到/终态，也不能把新的截止后申请伪装为旧申请。管理员仅可重试持久依据对应的失败退款。

T1必须同时保存原幂等键/参数指纹、initialAttemptId、受理操作记录和日志；T2若未留下结果，原请求重放或原initialAttemptId可恢复，不重新创建申请。同单最多一个未关闭USER依据，新键不能并发堆积申请。成功退款或订单因签到/正常结束不再具备退款资格时，关闭失效的其他依据并记录原因，避免永久阻塞注销。平台退款用平台依据，不能误计为主动退款；完整断点协议见api.md第4.4节。

### 9.4 验票

CHK-02 核对 → 先会话和当前场次授权 → 再显示必要姓名/场次/票种；CHK-03 确认时全部重查。窗口 `[startsAt-30分钟,endsAt)`。重复签到优先返回首次结果，但账号已失效或改绑先拒绝。签到与组织者取消串行竞争；已签到后组织者取消失败，合法取消先提交则新签到失败。

### 9.5 终止、自然结束与恢复

组织者只能在首场前且全活动没有签到时取消。管理员必须有核查事实才能下架；已终态只记违规不改终态。终止事务保存状态、生效时刻、用于判定每单资格的持久事实/待办，立即阻止所有新交易与验票，立即停用关联检票账号。事实捕获应在同一受控写边界完成，可采用终止项或不可变版本事实；不得在后台按新时刻重新判断。

内部任务逐单事务：未支付类取消；未结束场次未签到成功单退款；已签到完成；旧终态不动。全部结算后才发布正式报表。超期仍继续执行，记录未达标。自然场次结束也即时挡新验票，不等结算；整活动自然结束即时拒绝公开访问与检票账号请求，即使清理字段尚未落库。

已结束场次若自然结算积压，终止任务只能按原自然结束事实补办缺席/完成，不能漏掉或改为平台退款。已结算场次快照不重写；活动终止汇总等所有项完成。整活动计划结束已到时也禁止“趁状态尚未更新”下架或编辑。

终止通知另有持久接收人任务项，覆盖组织者、相关参与者和检票账号，不只遍历有订单的参与者；同事件同接收人去重，全部必发通知也计入5分钟目标。账号销毁不删除待发消息记录，不恢复该账号读取权限。

## 10. 数据设计与不变量

ID 统一 UUID 字符串，不用手机号、姓名当业务外键；订单姓名/金额保存快照，地点读取最新场次值。数据库时间可保存 UTC epoch 毫秒；API 统一北京时间带偏移的 ISO 字符串。金额整数角 `0..9999990`。

完整33张表、逐字段类型/空值/唯一性与完整建表命令见[MySQL设计](database-design.md)，Redis键见[Redis设计](redis-design.md)。下表是职责摘要，不是另一套物理命名。

| 表组 | 必需字段/约束 |
| --- | --- |
| users / phone_identities | 固定角色、规范化用户名/邮箱/手机号、哈希密码、逻辑删除、强制改密；有效账号唯一；手机号跨注销记录次数/黑名单/处罚身份 |
| login_sessions / recoveries | tokenHash、固定 issuedAt/expiresAt/revokedAt；人工核验依据；不保存或记录明文密码 |
| events / event_sessions / ticket_types | 归属、状态、类别快照、稳定子对象ID、时间窗口、容量、priceJiao、saleStopped、version |
| orders | user/session/type、姓名/金额快照、requestId/指纹、状态/原因/截止/占位事实；可空生成列active_guard+唯一索引，保证用户+场次有效唯一 |
| payment_attempts / refund_requests / refund_attempts | 每单成功支付/退款以success_guard生成列+唯一索引实现；支付order+attempt唯一；同单未关闭USER依据用open_user_guard+唯一索引；原依据、initialAttemptId、资格快照、撤销/关闭原因、原支付关联、每次结果 |
| tickets / checkins / checker_assignments | 每单一票、全局票号唯一、每票一签到；当前检票账号唯一授权；历史签到的人员和场次不回改 |
| event_reviews / publication_quotas | 审核结果/理由；北京时间日首次发布额度原子更新，取消不返额 |
| reports / investigations / behavior_facts / restrictions / restriction_facts | 人+场举报唯一；同活动同事实去重；依据消费防重复处罚；限制跨重注册 |
| messages / audit_logs | eventKey+recipient 唯一；业务成功同事务；失败日志单独事务尝试，不保存密码/令牌 |
| jobs / termination_facts / job_items | type、dueAt、deadlineAt、进度、租约/重试、终止时事实；任务+订单/接收人唯一；另有CSV持久任务，不靠内存游标 |
| statistics_snapshots / exports | 结算完成版本、分子分母、终止原因、expiresAt；导出文件受控路径、生成者、完整状态 |

数据库 CHECK/外键/唯一索引与领域校验共同维护：

- 同用户同场最多一有效单；有效集合=WAITLISTED/OFFERED/UNPAID/REGISTERED/CHECKED_IN。
- 同一用户重叠场次有效单互斥，时间半开区间，相邻场允许；须在同一写事务检查。
- 已占=UNPAID+OFFERED+成功出票未退款（含 REGISTERED/CHECKED_IN/COMPLETED/ABSENT）；剩余=票种容量−已占≥0。
- 场次余票=其票种余票之和，不把场次尚未分配到票种的容量当作可售票。
- 每单最多一成功支付、一成功退款、一票、一签到；支付与递补确认不重复扣占位。
- 票种必须属于订单场次；子对象不能跨活动复用 ID；不物理级联删除业务关联。
- `version` 防止两个管理页面互相覆盖，但不能代替实时库存/状态校验。

## 11. 字段与时间校验基线

活动/场次/票种名称 trim 后1～60字；地点1～60字；简介≤500字。按 Unicode code point 计长度，前后端一致。草稿允许字段缺失；已填写字段须合法，草稿容量总和允许不平衡；提交要求活动1～20场，每场1～10票种，容量1～9999且总和合法。

场次名在活动内、票种名在场次内唯一；ID不能重复或跨聚合复用。草稿允许暂缺必填项和容量总和不平衡，不允许已填写字段越界或已齐备的起止关系非法。活动计划起止、总容量、价格范围从配置计算为只读汇总；不能用它们携带过期订单统计。

场次起止整小时且结束>开始；前端先向下取整并展示用户确认，后端拒绝非整点值，不静默改既有时间。放票起止精确到分钟。提交时最早场次 `now < startsAt ≤ now+7天`，其他场不要求在7天内；逐场与组织者其他待审/已发布未终止活动比排期。发布时 `publishedAt ≤ salesOpensAt < registrationClosesAt ≤ startsAt`，错过开售必须说明原因退回草稿。

海报 JPEG/PNG 单张≤5,000,000字节（基线只写5MB，采用十进制保守上限，不再扩大解释为5MiB）；验证真实格式、大小并生成受控文件名。替换先验证新文件再原子切换，失败保留旧图。草稿/已发布管理 DTO 中不能伪造任意文件路径。

账号密码至少8位且仅ASCII字母数字、两类均有；成熟带随机盐哈希（计划 BCrypt），绝不明文保存。[Spring Security 密码存储说明](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)。用户名/邮箱 trim+ASCII大小写归一比较；手机号按中国大陆11位数字作为本原型设计输入约束。用户名1～60字、邮箱≤254字符、密码8～72个ASCII字符、本人姓名1～60字为实现上限选择；这些新增格式上限列入待审阅设计决定。

## 12. 会话、安全与数据保留

会话采用随机不透明 token 的 HttpOnly Cookie，后端只存 tokenHash；固定7天，不随访问续期，第二端登录撤销第一端；密码修改/重置、停用、注销立即撤销。使用 CSRF token 保护全部变更请求，登录/退出后重新取 token；同源开发代理与交付减少跨域配置。强制改密会话只允许读取本人最小资料、CSRF、改密和退出。[Spring Security SPA/CSRF 说明](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)。

检票账号的服务端有效性包括活动是否实际整体结束/终止；不能等待清理任务才禁止旧 token。最后一个可用检票账号不可从已发布未结束场次移走，先添加替代账号；改绑只允许同活动未结束场次。

| 数据 | 读取/保留期限 |
| --- | --- |
| 日常名单、正式统计、CSV文件 | 整活动实际终结后7天，到点所有角色拒绝查看、生成、重建、下载，之后逻辑清理 |
| 底层订单、支付、退款、票、签到 | 持续保留；活跃本人历史可读；管理员仅合法单条审计，禁止借此批量重建过期名单 |
| 操作日志 | 每条生成180天后物理删除；无人工修改删除或导出接口 |
| 消息 | 每条生成180天后逻辑删除；已读不延长其他业务期限 |
| 注销与手机号黑名单 | 长期保留；两次注销至少365天，第三次后永久禁该手机号注册 |

自然结束的保留起点是最晚计划场次结束；取消/下架为生效时刻，不覆盖原计划。到期读取拦截不依赖清理是否已运行。

## 13. 内部任务与运行指标

| 内部操作编号 | 触发与处理 | 时限目标 |
| --- | --- | --- |
| JOB-01 | 支付/递补确认到期、报名截止；取消未完成单、原子释放 | 触发后1分钟内 |
| JOB-02 | 释放/新增名额、停售恢复、锁定解除后公平递补 | 触发后1分钟内 |
| JOB-03 | 自然场次完成/缺席及快照、整活动结束汇总 | 结束后1分钟内 |
| JOB-04 | 取消/下架逐单结算、通知、终止报表 | 生效后5分钟内 |
| JOB-05 | 7天短期数据、180天消息日志清理、检票账号销毁 | 读取/登录到点即拒绝；后台周期清理 |
| JOB-06 | 限制恢复核对、到期解除及消息 | 正常组织者限制随事实事务即时生效；扫描不改原期限，到点解禁即时判断 |
| JOB-07 | MGT-02受理后异步生成CSV、完整文件发布与失败恢复 | 无额外课程处理时限；生成/发布/下载必须仍在数据有效期 |

计划以5秒调度周期扫描持久到期项，采用单执行器/租约避免同项重复；“周期5秒”不等于保证所有工作5秒完成。每项保存最初触发时刻、截止、完成时间及重试次数；停机重启扫描未完成项，超过1/5分钟记超时仍继续。无向普通用户开放任意触发内部任务的 HTTP 接口。

组织者合格违规事实达到3条时，事实、15天PUBLISH限制、依据消费、日志和通知同事务提交；发布入口实时复核，不等5秒扫描才生效。JOB-06负责恢复核对和到期解除，不重算既有开始时刻，也不在有效期内不断延长处罚。参与者仍由管理员核实后限制。CSV任务保存筛选条件，生成时用一致读快照记录dataAsOf，发布前复查期限，过期转EXPIRED而不是重建。

性能验收按 REQ-023：固定环境（≥4逻辑核/8GB、应用与MySQL/Redis在记录的同机环境；替代原SQLite参照重新验收）、10000活动×2场×2票种、50并发共100查询，四类各25次，≥95次成功且全响应≤1秒，失败/超时不剔除。并发容量按20个合格账号抢最后1名额，必须1未支付+19候补，再支付验证不重复占位。以上均为目标，尚未实测。

## 14. 并行开发与联调计划

此节定义可并行的工作边界，不表示已经启动代理或额外开发进程。

1. **契约与骨架**：审阅本组文档；创建前后端工程、锁定工具版本、API类型、迁移、统一异常/时钟/事务/身份、mock夹具。

3. **并行扩展**：前端按参与者/组织者/检票/管理员页面域推进，后端按 event/order/payment/ticket/governance/reporting 等模块推进；公共 DTO/枚举/错误码集中维护。
4. **边界与恢复**：候补、期限、退款重试、并发、终止任务、统计期限和注销；联调全角色、旧页面、断网重放与重启恢复。
5. **交付**：构建检查、类型/风格检查、关键业务验收、Git远程展示、源码规模统计、打包。实验报告由本人撰写。

同一阶段前端不等待数据库建好：先通过 api.ts + mock adapter 展示约定状态；后端用相同请求响应夹具验证契约。接口字段改变先改 api.md 与 TS/Java DTO，再改调用方；业务需求变化同时改追踪表。每次联调以一个完整垂直流程为单位，不能只凭页面可点击判定完成。

分工建议：前端负责 `frontend/`，后端负责 `backend/`，接口契约变更需要双方同步；多人在独立 `codex/` 分支提交，避免并发修改同一共享文件。运行库、node_modules、target、dist、凭据、个人数据不入 Git；迁移、锁文件、测试夹具、源码及构建脚本入 Git。
