## 1. 结论与可信边界

**v0.1不能认为已经100%正确。**它覆盖了53个需求编号，但“编号均出现”不足以证明接口字段、权限、异步边界和恢复协议正确。本轮识别并修订下列20组设计缺口、冲突或约定不完整之处，版本升为v0.2。没有发现需要整模块删除或改变已确认视觉方向的依据。

本轮是文档语义审查，不是软件运行验收：尚无Java/Vue业务代码、数据库迁移或真实请求可执行，不能证明事务、性能、界面步数或1/5分钟任务已经达标。修订后未保留已知、可直接定位的同类冲突，但仍不能保证没有未知问题。

## 3. 源需求内部的交叉解释

以下不是新增删除需求，而是按照主责条目/附录处理表面冲突：

| 表面冲突 | 本轮采用的解释 |
| --- | --- |
| REQ-003管理员可查全部支付记录 vs REQ-052到期仅单条审计 | 管理员对象范围可覆盖平台，不代表永久批量枚举权；有效期内列表，过期通过明确单条业务编号审计/合法退款依据处理，不重建整活动名单 |
| REQ-015退款失败全部回滚 vs REQ-003合法原申请可重试 | 退款/票/订单/库存执行事务全部回滚；先前独立持久化的合法受理依据和失败尝试不因此消失，且不把订单置REFUNDING |
| REQ-018已过验票窗口可查首次结果 vs REQ-031整活动结束销毁检票账号 | 当前账号和当前授权校验优先；多场活动某场结束但账号仍有效可查首次结果，整活动结束失效后不可登录查询 |
| REQ-022已结束场次终态不变 vs 异步结算可能尚未产生终态 | 已有终态不改；尚未结算的该场按原自然事实补结算，不能改平台退款，不伪装已完成验收 |
| REQ-043锁定新报名 vs REQ-013已有候补保位 | 新申请拒绝；原WAITLISTED保位但跳过新占位，原OFFERED/UNPAID继续原期限履约；业务限制不等于停用账号 |

## 4. 仍属于设计选择、尚非甲方确认的项目

这些内容已明确为v0.2待审阅设计，不作为phase1原文规定。若用户调整，应同步Java/TS模型、校验和夹具，不能只改页面：

- 大陆11位手机号、用户名/本人姓名/证据文本的具体上限、BCrypt对应的密码72位上限；原基线没有完整规定这些格式上界。
- Cookie/CSRF、hash路由、UUID、聚合保存、版本号、通用幂等记录180天、海报字节单位、只读汇总字段及最后管理员保护等实现选择。
- 同活动内场次是否允许时间重叠：基线明确检查“其他活动”和参与者有效订单冲突，未明确禁止本活动内部重叠；本轮不擅自新增禁令，保留逐场交易冲突检查。
- 技术依赖的精确版本尚待工程初始化锁定；SQLite事务及查询性能必须在实际选定驱动/版本上验证。

以上未决设计不阻碍阅览本轮接口草案，但不应被写成用户已经同意的新增业务规则。
